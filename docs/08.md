## 8.1 問題の分解と考察

**霊夢**: 赤色って、テンプレが分かっても解けないことが多いのよね……

**魔理沙**: その感覚は正しい。橙色まで来ると **「典型の型」** は揃っている。赤色で増えるのは **問題文の翻訳** と **複数の技法の合成** だ。まず「何を聞いているか」を日本語に直す。実装はそのあとでいい。

**霊夢**: いきなりコードを書くと、サンプルで WA して終わるパターン……

**魔理沙**: だから [02.md](02.md) の全探索・[03.md](03.md) の BFS/DP と同じく、**紙のチェックリスト** を先に書く。次の 5 段階を 3 分で埋めれば、解法候補が 3 個までに絞れる。

| 段階 | 質問 |
|------|------|
| 制約 | N, Q, 値域、mod、木か一般グラフか |
| 弱い制約 | 小さい N で全探索・MITM が効くか |
| 強い制約 | 線形・対数・√ しか通らないか → データ構造の候補 |
| 言い換え | 「操作の列」→「不変量」「潜在値」「グラフ上の状態」 |
| 部分点 | 小さいケースだけ先に AC してヒントにする |

### 考察の手順（イメージ）

1. **制約を数で書く** — `N=2×10^5`, `Q=10^5`, `|A_i|≤10^9` のように、変数名ごとにメモ  
2. **オーダーを当てる** — `N×Q` は 4×10^10 で無理 → 対数か √ か線形のどれか  
3. **弱い制約を探す** — `N≤18` なら bitmask、[07.md](07.md) の MITM  
4. **言い換え** — 「操作」が **グラフの辺**・**セグ木の区間更新**・**DP の状態** のどれに見えるか  
5. **部分点** — 小さい `N` だけ先に提出して、本番のヒントにする（AGC D〜F でよく効く）

### 問題文で「分解」を疑うキーワード（いつ使う）

| キーワード・制約の形 | まず疑うこと |
|----------------------|--------------|
| 操作が 10^5 回、配列を更新・クエリ | セグ木・Fenwick・SegBeats・Wavelet（[8.2](#82-先進的データ構造)） |
| `N≤20` 前後 | bitmask、meet-in-the-middle |
| 木・根付き木・パス上のクエリ | LCA、HLD（[07.md](07.md)） |
| 一般グラフ・割当・流れ | 最大流、マッチング、2-SAT |
| 「合成」「畳み込み」「多項式」 | NTT・モノイド（[8.3](#83-代数構造と競プロ)） |
| 部分和・順列・最適化で探索 | 枝刈り・下界（[8.4](#84-計算量の下限と最適化)） |

### 計算量の読み方（赤色）

| 制約の積 | 目安 | 例 |
|----------|------|-----|
| ≤ 10^6〜10^7 | O(N), O(N log N) | 線形走査、ソート、セグ木 1 回 |
| ≤ 10^8 前後 | O(N √N), 軽い定数の O(N log N) | Mo's、軽いセグ木 |
| ≤ 10^9〜10^10 | ほぼ無理（Py では特に） | 別アルゴリズムか部分点を探す |

**霊夢**: `2×10^5 × log` は通るの？

**魔理沙**: `2×10^5 × log(2×10^5) ≈ 3.6×10^6` 程度だから、**セグ木 1 クエリ O(log N)** なら Q=10^5 でも通ることが多い。逆に `N×Q` の素朴ループは 4×10^10 で TLE 確定だ。

### つまずき

| 症状 | よくある原因 |
|------|--------------|
| 解法が 10 個出て決められない | 制約の **オーダー当て** をしていない。表の「強い制約」から逆算する |
| サンプルは合うが本番 WA | 言い換えが違う（例: 最小化問題を貪欲にした）→ [8.5](#85-赤色演習読解と再現) の「否定」で反例を 1 つ |
| 部分点だけ取りたい | 弱い制約のサブタスクを見落としている。問題文の **制約表** を最初に読む |
| 解説を読んでも再現できない | テンプレ名を書かずに読んでいる → `SegBeats`, `NTT` など **名前付きでメモ** |

## 8.2 先進的データ構造

**霊夢**: セグ木の応用、まだ足りない？

**魔理沙**: [04.md](04.md)〜[07.md](07.md) で **区間和・区間 max・遅延伝播** は触れたはずだ。赤色で増えるのは **「普通のセグ木では落ちない更新」** をどう落とすか、と **静的配列の順位クエリ** だ。代表は **Segment Tree Beats**（区間 chmin + 和）、**モノイドセグ木**、**Wavelet Tree**（k 番目・ランク）の 3 つ。まず **存在と用途** を押さえ、実装は solutions から持てばいい。

**霊夢**: 3 つとも「区間クエリ」っぽいけど、違いは？

**魔理沙**: ざっくり言うと、**SegBeats** は「区間 chmin + 和」、**モノイドセグ** は「演算を差し替えた汎用セグ木」、**Wavelet** は「区間の k 番目・値の個数」だ。次の小節でそれぞれ **直感 → いつ使う → 計算量 → つまずき** の順に見る。

### Segment Tree Beats（区間 chmin）

**霊夢**: chmin って、区間の最大値を `x` 以下に押さえる操作？

**魔理沙**: そう。**区間 chmin** と **区間和クエリ** が同時に来ると、普通の遅延セグ木では「max を下げたあと和をどう更新するか」が重くなる。SegBeats は各ノードに **最大値 `mx`・その個数 `cnt`・第二最大 `se`・区間和 `sum`** を持ち、「この区間の max が `x` 未満なら何もしない」「max だけが `x` より大きく、第二 max は `x` 未満なら lazy に一括 chmin」という **beats（打ち負かし）** で落とす。

#### アルゴリズムの直感

1. 葉では `mx = sum = 値`, `cnt = 1`, `se = -∞`  
2. 親は左右の `mx` の大きい方を採用し、`cnt` と `se`（第二最大候補）をマージ  
3. **区間 chmin(x)** で、ノード全体の max が `x` 以下なら return  
4. **`se < x < mx`** のときだけ、そのノードの max 要素だけを `x` に落とし、`sum` から `(mx-x)×cnt` を引く（個別に葉まで降ろさない）  
5. それ以外は子に再帰してから `push_up`

**霊夢**: 「第二最大」があるから、max だけ触れるってこと？

**魔理沙**: その理解で十分。区間に max が 1 種類だけなら lazy で済む。2 種類以上混ざる区間だけ子に降りるので、**均摊** でクエリが通る。

#### いつ使うか

| 問題文のキーワード | SegBeats を疑う |
|--------------------|----------------|
| 区間 chmin / 区間 min に更新 | ○（chmin 系） |
| 更新のあと区間和・区間 max | ○ |
| 区間加算 + 区間和 | 通常の lazy セグ木（[04.md](04.md)） |
| 区間の k 番目 | Wavelet（次の節） |

#### 計算量

| 操作 | 目安 |
|------|------|
| 構築 | O(N) |
| 区間 chmin / 区間和 | **均摊** O(log N)（問題によっては O(log² N) と書かれることも） |
| メモリ | O(N)（4 倍配列が多い） |

#### つまずき

| 症状 | 対処 |
|------|------|
| `se` の更新を間違える | `push_up` で左右の max を比較し、**大きい方の `se` と、小さい方の `mx` の max** を混ぜる（下の `_push_up` を solutions と突き合わせ） |
| chmin 後の和が合わない | `_apply_chmin` で `sum -= (mx - x) * cnt` を忘れていないか |
| 全区間 chmin が TLE | 均摊が効く条件を満たしているか（値域・更新の型）。別解法（潜在値・差分）も検討 |

→ [solutions/python/08/segbeats/](../solutions/python/08/segbeats/) / [solutions/go/08/segbeats/](../solutions/go/08/segbeats/)

```python
class SegBeats:
    def __init__(self, arr):
        n = len(arr)
        self.n = n
        size = 4 * n
        self.sum = [0] * size
        self.mx = [0] * size
        self.se = [0] * size
        self.cnt = [0] * size
        self._build(arr, 1, 0, n - 1)

    def _push_up(self, i):
        self.sum[i] = self.sum[i * 2] + self.sum[i * 2 + 1]
        mx1, mx2 = self.mx[i * 2], self.mx[i * 2 + 1]
        if mx1 >= mx2:
            self.mx[i], self.se[i], self.cnt[i] = mx1, self.se[i * 2], self.cnt[i * 2]
        else:
            self.mx[i], self.se[i], self.cnt[i] = mx2, self.se[i * 2 + 1], self.cnt[i * 2 + 1]
        if self.se[i] < mx1:
            self.se[i] = max(self.se[i], mx1 if mx1 < mx2 else mx2)
```

**霊夢**: 本文のコードは `_push_up` までだけど、chmin 本体は solutions ？

**魔理沙**: そう。上のブロックは **ノードのマージの心臓** だ。`range_chmin` と `range_sum` の全文は [segbeats/](../solutions/python/08/segbeats/) にある。本番は solutions をコピーして、問題に合わせて `apply` だけ直せ。

### モノイドセグ木

**霊夢**: モノイドって、[8.3](#83-代数構造と競プロ) で出てくるやつ？

**魔理沙**: 先取りするな。競プロでは **「結合する演算 `op` と単位元 `e` が決まっている」** だけ分かれば動かせる。`(max, -∞)`, `(+, 0)`, `(gcd, 0)` などを **同じ `MonoidSeg` クラス** に渡す。区間クエリ・一点更新は [04.md](04.md) のセグ木と同じ構造で、**型を汎用化した** イメージだ。

#### アルゴリズムの直感

1. 葉配列を **完全二分木**（サイズ 2 の冪）の下半分に置く  
2. 親は `dat[i] = op(dat[2i], dat[2i+1])` で構築  
3. **区間 [l, r)** クエリは、葉に対応するインデックスを `+= size` してから、端が奇数になるたびに `dat` を `op` で拾い上げる（2 つのスタック `left`, `right`）  
4. **一点更新** は葉を書き換えて根まで `op` で巻き上げ

**霊夢**: 遅延伝播は？

**魔理沙**: モノイドセグは **一点更新・区間取得** が基本。区間に同じ値を足すなどは、演算と lazy の設計が別問題になる（[04.md](04.md) の lazy 版を使うか、SegBeats など別構造を選ぶ）。

#### いつ使うか

| 欲しいクエリ | `op` / `e` の例 |
|--------------|-----------------|
| 区間 max | `max`, `-10**18` |
| 区間和 | `lambda a,b: a+b`, `0` |
| 区間 gcd | `math.gcd`, `0` |
| 区間 xor | `lambda a,b: a^b`, `0` |
| 文字列結合 | `+`, `""`（長さ制限に注意） |

#### 計算量

| 操作 | 目安 |
|------|------|
| 構築 | O(N) |
| 区間クエリ・一点更新 | O(log N) |
| メモリ | O(N)（2 倍木） |

#### つまずき

| 症状 | 対処 |
|------|------|
| 区間 [l, r) の半開区間を閉区間と混同 | AtCoder は **0-indexed 半開 [l, r)** が多い。`query(l, r)` のループ条件を solutions と揃える |
| `gcd` で `e=0` がおかしい | `gcd(a,0)=a` なので競プロでは `e=0` でよい |
| `max` の単位元が小さすぎる | `-10**18` や `-inf` を **データより十分小さい値** に |
| 同じコードを何度も書く | `MonoidSeg` 1 本 + `op,e` 差し替えで [07.md](07.md) 以降のコピペ地獄を減らす |

→ [solutions/python/08/monoid_seg/](../solutions/python/08/monoid_seg/) / [solutions/go/08/monoid_seg/](../solutions/go/08/monoid_seg/)

```python
class MonoidSeg:
    def __init__(self, data, op, e):
        self.n = len(data)
        self.op = op
        self.e = e
        size = 1
        while size < self.n:
            size <<= 1
        self.size = size
        self.dat = [e] * (2 * size)
        for i, x in enumerate(data):
            self.dat[size + i] = x
        for i in range(size - 1, 0, -1):
            self.dat[i] = op(self.dat[i * 2], self.dat[i * 2 + 1])
```

**魔理沙**: Go では `op` と `e` を struct にまとめて `MonoidSeg` に渡す形が多い（[monoid_seg/](../solutions/go/08/monoid_seg/) 参照）。

### Wavelet Tree（入門）

**霊夢**: Wavelet……名前だけで難しそう。

**魔理沙**: **静的配列**（あとから値が変わらない）に対して、**区間 [l, r) の k 番目の値** や **値 v の個数（ランク）** を速く引く木だ。セグ木が「インデックス軸」で区切るのに対し、Wavelet は **値の大小で二分** しながら、各レベルで「左の子に落ちるか」をビット列で記録する。

#### アルゴリズムの直感

1. 値域を座標圧縮し、全体を `[lo, hi]` の値域で見る  
2. 中点 `mid` より大きい要素に 1、小さい方に 0 の **累積ビット** を作る（ランククエリ用）  
3. **k 番目** — ルートから、区間 [l,r) で左に落ちる個数が k より多いかで左/右の子へ、値域も半分に  
4. **静的** が前提。点更新が必要なら永続セグ木・平衡木など別候補（[07.md](07.md)）

**霊夢**: 本文の `break` は途中で止めてるの？

**魔理沙**: 意図的だ。下のブロックは **1 レベル分のビット構築** のイメージだけ示す。再帰で子配列を分ける全文は [wavelet/](../solutions/python/08/wavelet/) を見ろ。

#### いつ使うか

| 問題文のキーワード | Wavelet を疑う |
|--------------------|----------------|
| 区間の k 番目の値 / median 風 | ○ |
| 区間内で値 v が何個 | ランク ○ |
| 動的に要素を追加・削除 | ×（静的向け） |
| 区間和・区間 chmin | セグ木・SegBeats |

#### 計算量

| 操作 | 目安 |
|------|------|
| 構築 | O(N log σ)（σ は値域・圧縮後の種類数） |
| k 番目・ランク | O(log σ) |
| メモリ | O(N log σ) |

#### つまずき

| 症状 | 対処 |
|------|------|
| 実装が長すぎて本番で書けない | **テンプレを solutions から持つ**。赤色は「初めてゼロから書く」より「転用」が多い |
| k が 0-indexed か 1-indexed か | 問題文の定義をサンプルで確認 |
| 動的更新が必要なのに Wavelet | 永続セグ木・`std::multiset` 風の平衡木を検討 |
| σ が巨大 | 座標圧縮を忘れるとメモリ・時間が爆発 |

→ [solutions/python/08/wavelet/](../solutions/python/08/wavelet/) / [solutions/go/08/wavelet/](../solutions/go/08/wavelet/)

```python
class Wavelet:
    def __init__(self, arr):
        self.arr = arr
        self.n = len(arr)
        vals = sorted(set(arr))
        self.comp = {v: i for i, v in enumerate(vals)}
        self.levels = []
        lo, hi = 0, len(vals) - 1
        while lo < hi:
            mid = (lo + hi) // 2
            bit = [0]
            for x in arr:
                c = self.comp[x]
                bit.append(bit[-1] + (1 if c > mid else 0))
            self.levels.append((lo, hi, mid, bit))
            # 次のレベルへ分割（実装は solutions 参照）
            break
```

**霊夢**: Wavelet は実装が長い……

**魔理沙**: まず **存在と用途** を押さえ、本番は [solutions/](../solutions/python/08/wavelet/) から持てばいい。ARC E で「区間 k 番目」が出たら、セグ木より Wavelet を候補に入れろ。

## 8.3 代数構造と競プロ

**霊夢**: 群とか環って、大学数学？

**魔理沙**: 厳密な定義は教科書に任せる。競プロでは次の **機械的な対応** だけ押さえれば足りる。

| 構造 | 競プロでの意味 | 例 | 典型用途 |
|------|----------------|-----|----------|
| **モノイド** | 結合律 + 単位元 `e` | (max, -∞), (+, 0) | セグ木、ダブリングの合成 |
| **群** | 逆元が取れる | mod 998244353 の加法 | 累積、期待値、差分の逆操作 |
| **環** | 2 つの演算（+ と ×） | 多項式係数 | NTT 畳み込み、生成関数 |

**霊夢**: 「操作が合成できる」って言うと、何に繋がるの？

**魔理沙**: 次のどれかに落ちると判断する。

1. **区間にまとめて適用** → セグ木・MonoidSeg（[8.2](#82-先進的データ構造)）  
2. **k 回繰り返す** → ダブリング・行列べき乗（[06.md](06.md)）  
3. **2 列を混ぜ合わせる** → 畳み込み（下の NTT）

### 畳み込み（convolution）の直感

多項式 `A` と `B` の積の係数は、`C[k] = Σ A[i]*B[j] (i+j=k)` という **「足し合わせて k になる組」** の和だ。ナイーブは O(N²)。**NTT** は「係数列を点評価に変換 → 点ごとに掛ける → 逆変換」で O(N log N) にする。[07.md](07.md) で触れた mod 998244353 と原根 3 を使う型が AtCoder の定番だ。

#### いつ使うか

| キーワード | 畳み込みを疑う |
|------------|----------------|
| 畳み込み、組み合わせ数列の積 | NTT / FFT |
| 区間の選び方 + 重みの積 | 生成関数 |
| 「○回操作」の数列カウント | DP + NTT |
| 文字列の一致回数（小さいアルファベット） | FFT（別枠） |

#### 計算量

| 手法 | 目安 |
|------|------|
| ナイーブ畳み込み | O(NM) |
| NTT | O(N log N)（長さを 2 の冪にパディング） |

## 8.4 計算量の下限と最適化

**霊夢**: もう計算量のオーダーは分かるのに、TLE する……

**魔理沙**: 理論オーダーが合っていても、**定数 2 倍** で落ちることはある。赤色 TLE の多くは **枝刈り不足・入出力・再帰・コピー** だ。アルゴリズムを変える前に、プロファイルのように **どこが重いか** を当てる。

| 技法 | 内容 |
|------|------|
| 枝刈り | 上界・下界で探索を切る（例: 部分和） |
| 定数削減 | `sys.stdin.buffer`、再帰→反復、配列の再利用 |
| メモリ | `__slots__`、不要なコピー削減 |
| 並列化 | PyPy / Go / C++ への切り替え |

### 枝刈り（branch and bound）の直感

深さ優先で候補を試すとき、**「この先を全部足しても目標に届かない」** なら return する。部分和では、残り要素の和 `sum(xs[i:])` が残り目標 `rem` より小さいとき、以降を選んでも成功しないので打ち切れる。さらに **大きい値から先に試す** と、早く解が見つかり、枝刈りが効きやすい。

#### いつ使うか

| キーワード | 枝刈り DFS を疑う |
|------------|-------------------|
| 部分和・ナップサック風・bit 全探索の前 | ソート + 残和打ち切り |
| 順列・配置の全探索 | 現在のコスト + 下界 > 最良値 |
| 理論 O(2^N) だが N≤40 前後 | MITM と併用（[07.md](07.md)） |

#### 計算量

| 手法 | 目安 |
|------|------|
| 素朴 DFS | 最悪 O(2^N) |
| 枝刈りあり | 最悪は同じだが **平均的に大幅削減**（データ依存） |
| ソートの前処理 | O(N log N) |

#### つまずき

| 症状 | 対処 |
|------|------|
| 枝刈りしても TLE | 探索順序（降順ソート）、下界の強さ、MITM への切り替え |
| 打ち切りで解を見逃す | `sum(xs[i:]) < rem` は「残り全部足しても足りない」だけ切る。不等号の向きを確認 |
| 再帰が深すぎる | `sys.setrecursionlimit` または反復 + 明示スタック |
| Python だけ遅い | 同じロジックを Go で書く（下の solutions） |

→ [solutions/python/08/branch_bound/](../solutions/python/08/branch_bound/) / [solutions/go/08/branch_bound/](../solutions/go/08/branch_bound/)

```python
def subset_sum_pruned(xs, target):
    xs = sorted(xs, reverse=True)
    best = [False]

    def dfs(i, rem):
        if rem == 0:
            best[0] = True
            return
        if rem < 0 or i == len(xs):
            return
        if sum(xs[i:]) < rem:
            return
        dfs(i + 1, rem - xs[i])
        if best[0]:
            return
        dfs(i + 1, rem)

    dfs(0, target)
    return best[0]
```

**霊夢**: 「理論上は通るのに通らない」は心が折れる……

**魔理沙**: まず **部分点の小さい制約** で正しさを固め、定数は後から。AGC F はここが勝負になることもある。枝刈りは **正しさを変えずに探索回数だけ減らす** 技法だと覚えろ。

## 8.5 赤色演習：読解と再現

**霊夢**: 長編って、一問ずつじっくり？

**魔理沙**: 赤色の学び方は **読む → 真似る → 伸ばす** の 3 段。いきなり E/F をゼロから AC しようとすると燃える。**読解ログ** を残し、同じ技法の別問題に転用する方が再現率が上がる。

| 段階 | やること | 時間の目安 |
|------|----------|------------|
| 読む | 制約・サンプル trace・解法候補 3 個 | 20〜40 分 |
| 真似る | 公式解説を読み、テンプレ名をメモして部分実装 | 1〜2 時間 |
| 伸ばす | 同タグの別問題を 1 問（完コピ不要） | 週 1 問程度 |

**霊夢**: 全文 AC コードは載せないの？

**魔理沙**: この節は **読解の型** が主役だ。実装は [Part 0〜7](../solutions/python/) と [8.2](#82-先進的データ構造) のテンプレを組み合わせる。ログ用の Markdown 雛形だけ下に置く。

### 例: 難問を「翻訳」する（arc170_e 風の読み方）

**霊夢**: 問題文が長い……

**魔理沙**: 次の順でメモを取れ。コードを書く前に **5 ステップ** を紙か `study_log` に埋める。

1. **入力・出力** を 1 行ずつ日本語化  
2. **サンプル 1** を手で trace（5 分）  
3. **あり得る解法タグ** を 3 個まで書く（例: 「フロー」「DP」「データ構造」）  
4. **否定**: なぜ greedy だけではダメか、反例を 1 つ  
5. **公式解説を読んだあと**: 自分のメモと diff を 3 行  

### study_log の使い方（いつ使う）

| タイミング | 書く内容 |
|------------|----------|
| 問題を開いた直後 | 制約メモ、サンプル trace |
| 手を止めたとき | 詰まった理由（「SegBeats か HLD か迷う」など） |
| 解説を読んだ後 | 公式解説との diff、使ったテンプレ名 |
| 1 週間後 | 同じ技法の別問題 ID を 1 行追加（再現チェック） |

### 計算量（学習ペース）

| ペース | 目安 |
|--------|------|
| 読解のみ | 週 2〜3 問（ARC E 相当） |
| 実装まで | 週 1 問（部分点可） |
| 連続で E/F を何問も | 非推奨（燃え尽き防止） |

### つまずき

| 症状 | 対処 |
|------|------|
| 解説を読んでも真似れない | diff に **テンプレ名**（`SegBeats`, `NTT`）を必ず書く |
| メモが長すぎる | 解法候補は **3 個まで**。否定は反例 1 つだけ |
| 完コピして次の問題で真似できない | 「転用」欄に **何を変えたか** を 1 行書く |
| ログを残さない | 下の `STUDY_TEMPLATE` をファイルごとコピー |

→ [solutions/python/08/study_log/](../solutions/python/08/study_log/) / [solutions/go/08/study_log/](../solutions/go/08/study_log/)（再現用テンプレ）

```python
STUDY_TEMPLATE = """
# 問題 ID:
# 日付:
## 制約メモ
## サンプル trace
## 解法候補 (最大3)
## 実装メモ (テンプレ名)
## 公式解説後の diff
"""
```

**魔理沙**: 再現週間では **同じ技法の別問題** を 1 問だけ解く。完コピより **テンプレの転用** を狙え。ログは Git やローカル Markdown でよい。リポジトリの [study_log/](../solutions/python/08/study_log/) は雛形の置き場だ。

**霊夢**: diff って、git の diff？

**魔理沙**: ここでは **「自分の予想と公式解説の差分」** の意味だ。「フローだと思ったが DP+セグ木だった」など 3 行でよい。
